Claude Account Switcher

How claude-acct.sh rotates several Claude subscriptions on one Mac by swapping the live account in place. Written 2026-10-30 against Claude Code 2.1.312-2.1.314 on macOS; updated 2026-11-06 for 2.1.317-2.1.319 (who follows a switch, quota readings, refresh-token rotation). Code: github.com/bradfeld/claude-acct. Account names below are examples.

1command to switch every new session and Claude in Chrome
2records moved per switch (token + identity)
5subscriptions in the rotation
95hermetic tests, all passing (run 2026-11-06)

The short version. Claude Code keeps one account in two places: an OAuth token in the macOS Keychain and an identity record in .claude.json. claude-acct.sh parks each account's pair in its own Keychain slot, and use <alias> swaps both into the live positions, verifies with claude auth status, and rolls both back if anything fails. It never creates a second config directory, so hooks, rules, skills, MCP logins, and session history stay shared. It never handles a token outside the Keychain and the unmodified claude binary.

1. Why swap in place

There are two ways to run several subscriptions on one machine. One is a config directory per account, chosen when a session starts (the claude-rotator model). The other is one config directory with the account swapped underneath it. I chose the second for three reasons specific to how this machine is set up.

  • The config directory is the whole machine surface. CLAUDE_CONFIG_DIR relocates hooks, rules, settings, skills, agents, commands, plugins, transcripts, the session registry, and the background-session supervisor's roster. Mine is large and heavily gated. A second directory per account means either symlinking a fixed list of entries (and missing whatever is not on it) or running several diverging machines.
  • The Keychain namespace follows the config directory. The credential item's name is a hash of the CLAUDE_CONFIG_DIR string (section 2). A login written under one directory is invisible to sessions that resolved another, and every MCP server's OAuth login lives in the same item, so a directory per account means signing in to every MCP server once per account.
  • Sessions are long-lived. I run many Claude Code sessions at once, and many live for days. Picking the account at launch only helps new sessions. Swapping in place gives new sessions the new account immediately and gives running sessions a path to follow (section 9).

2. Where Claude Code keeps an account

This is the part that took measurement rather than reading. The first version of the script swapped only the token, and it did not work: the Keychain write and read-back succeeded, then claude auth status still named the previous account, so the script rolled back. The token carries no identity at all.

1. The token

macOS Keychain, generic password

Service Claude Code-credentials, plus -<first 8 hex of sha256($CLAUDE_CONFIG_DIR)> when that variable is set, account $USER. (CLAUDE_SECURESTORAGE_CONFIG_DIR, when set, replaces the directory in the hash; set to empty, it drops the suffix.) The value is JSON. Key claudeAiOauth holds exactly: accessToken, refreshToken, expiresAt, refreshTokenExpiresAt, scopes, subscriptionType, subscriptionTypeSource, rateLimitTier. No email, no account id.

The same item also holds every MCP server's OAuth login and device keys. The live item is about 6 KB.

2. The identity

$CLAUDE_CONFIG_DIR/.claude.json, or ~/.claude.json on a stock install

Key oauthAccount: emailAddress, account UUID, organization UUID, and related fields. claude auth login writes it. claude auth status and the API's user attribution read it, not the token. Read from the 2.1.312 binary: s.email=E?.emailAddress??null, s.orgId=E?.organizationUuid, where E is the oauthAccount object.

Running sessions write this file often, under their own lock (section 7).

Consequence. A switch must move both records together and restore both together. Moving the token alone leaves Claude Code naming the old account over the new account's token. Moving the whole Keychain item instead of the one key logs every MCP server out, or into the wrong account's grants. So only the claudeAiOauth key moves, and every other key in the item stays byte-for-byte as it was.

3. Slots and the accounts file

Each account is parked in its own Keychain generic password, service claude-acct/<email>, holding:

{ "claudeAiOauth": { ...the token object... },
  "oauthAccount":  { "emailAddress": "...", ...identity... } }

A slot never holds MCP logins. Those stay in the live item. A slot saved before the identity fix carries only the token, and use refuses it, because the identity cannot be derived from the token and I will not call an undocumented endpoint to guess it. One add rebuilds it.

Aliases and Chrome profiles live in an optional tab-separated file, ~/.config/claude-acct/accounts:

# alias   email                    chrome profile directory
home      you@personal.example     Profile 3
work      you@company.example      Profile 4
fund      you@fund.example         Profile 8
...

The profile directory is the last segment of "Profile Path" on chrome://version.

Refresh tokens land about four weeks out from the sign-in. Past that date a parked slot cannot sign in at all, so list carries the date and the re-add command.

5. What use does, step by step

  1. Resolve. The alias becomes an email through the accounts file, and the result must pass a strict address regex. This is the input boundary, because the email becomes part of a Keychain service name (section 10).
  2. Take the script lock. One save, add, or use runs at a time (section 10).
  3. Read the target slot and check it: it must hold a claudeAiOauth object and an oauthAccount whose email is the slot's email. Otherwise refuse, exit 2.
  4. Read the live records as one account. Three reads: the label from claude auth status, the token item from the Keychain, the identity from .claude.json. The identity must name the same account as the status, and the status is read again after both byte reads, so a login or refresh landing in between cannot file one account's records under another's name.
  5. Compose the new live item before touching anything: the current live item with only claudeAiOauth replaced (jq -s '.[0] + {claudeAiOauth: .[1]}'). Every exit 2 up to this point still means nothing changed.
  6. Park the outgoing account from those same reads. Its token may have refreshed since it was last saved, so the slot is always rewritten with the current one. A failed park stops the switch.
  7. Write the token into the live Keychain item and verify by read-back hash (section 6).
  8. Write the identity into .claude.json under Claude Code's own config lock and verify the read-back email (section 7).
  9. Confirm with claude auth status, retried up to three times, because an empty read means "could not ask", not "wrong account".
  10. On any failure in 7-9, restore both the original token and the original identity, and exit 3 (or 4 if the restore fails). The identity is rewritten only if it actually moved, so "the write failed" never turns into "the restore failed".
  11. Record {ts, from, to} in ~/.local/state/claude-acct/switches.jsonl (mode 0600).
  12. Open the target's Chrome profile and print what moves: new sessions now, running sessions at their next request. If a plaintext .credentials.json exists, warn (section 9).

6. Writing the Keychain item

The script writes the item exactly the way Claude Code does, through /usr/bin/security, so the item's access list keeps trusting the same binary.

  • Transport. When the command line fits, the payload goes to security -i on stdin as add-generic-password -U -a … -s … -X <hex>. When it does not, it goes as -X <hex> in argv. The limit is 4032 bytes, the constant in Claude Code's own writer. I measured the two traps: -i silently truncates past that length and exits 1, and the -w stdin prompt keeps only the first 128 bytes. The ~6 KB live item takes the argv branch, as it already does on every token refresh Claude Code performs.
  • -U keeps the access list. Measured on a throwaway keychain: the trusted-application list was byte-identical before and after an -U update.
  • Every write is read back and compared by SHA-256 prefix. A write is only a success if the bytes came back.
  • A failed slot write is put back. If a slot write lands damaged, the previous value is restored; if there was none, the half-written slot is deleted. Exit 2 keeps meaning nothing changed.

7. Writing .claude.json under Claude Code's lock

Running sessions rewrite .claude.json constantly. Claude Code serializes those writes with a proper-lockfile mkdir lock at .claude.json.lock (read from the 2.1.312 binary: lockfilePath||`${e}.lock` plus fs.mkdir, returning ELOCKED on EEXIST), and its writer re-reads the file when the mtime moved before applying its change.

The script takes the same lock:

  1. mkdir .claude.json.lock, retrying every 100 ms for up to 5 seconds. It never steals the lock. A holder past the wait means the write failed, and the caller restores.
  2. Re-read the file under the lock, require valid JSON, and change oauthAccount only: jq --argjson a "$acct" '.oauthAccount = $a'.
  3. Write to a temp file created under umask 077, chmod it to the original mode (0600), and mv it over the original.
  4. Release the lock, then verify that the email read back is the target's.

A missing or corrupt .claude.json is refused and never created or truncated. A signal mid-write still releases the lock and removes the temp file through an EXIT trap.

8. Chrome profiles

Claude in Chrome must be signed in to the same claude.ai account as Claude Code, or its browser tools report "Browser extension is not connected". With one Chrome profile, every switch means signing out and back in. The fix is one Chrome profile per account, each signed in to claude.ai and the extension once, permanently. A switch never signs anything out; use just runs open -na "Google Chrome" --args --profile-directory="Profile N" to bring the right one forward.

add has the opposite problem: the sign-in page must open in that account's profile, and twice an approval went to whichever window happened to be frontmost. Claude Code opens its login URL by exec'ing $BROWSER with the URL as its one argument (also read from the binary). So add writes a two-line shim into a private temp directory and runs claude auth login with BROWSER pointing at it:

#!/bin/bash
exec open -na "Google Chrome" --args --profile-directory="$CLAUDE_ACCT_CHROME_PROFILE" "$1"

After the login, the script refuses to save unless claude auth status names the account it asked for.

9. Who follows a switch

Session kindFollows?Detail
New interactive sessionYes, immediatelyIt reads the live Keychain item and .claude.json at start.
Running interactive sessionYes, at its next requestBefore each request Claude Code re-reads the Keychain login and adopts a changed one (its "sibling login" adoption, read from the 2.1.317 binary). Measured 2026-11-04 with no restart: three running sessions' 7-day quota readings moved to the new account's reset window within about two minutes of a use. An idle session moves when next used. The 2026-10-29 reading that sessions "kept billing the old account for hours" came from an analytics user.email label, not the token the requests were sent with. For a session that did not move, /exit then claude --continue moves it with its conversation intact.
Session with CLAUDE_CODE_OAUTH_TOKEN in its environmentNeverIt stays on that token's account, which is useful for an unattended job that must not move.
Sandboxed launchd jobNeverThe sandbox denies the Keychain, so it cannot see a swap at all.

The .credentials.json trap. When a Keychain write fails, Claude Code falls back to writing a plaintext $CLAUDE_CONFIG_DIR/.credentials.json. Its mere presence makes the cross-process auth change detector watch that file's mtime instead of the Keychain, so a login in one window silently never reaches any other running session. It recurred six times in three weeks here, once 43 minutes into a session. A launchd job (WatchPaths on the file plus a 300-second interval) moves it aside within about five minutes, and use warns if it is present. Claude Code 2.1.286's release notes say this is fixed upstream; I keep the reaper until I have seen that.

10. Safety properties and residual risk

  • It never prints a credential. Values live in shell variables and move through pipes. Tests assert that use and list print nothing token-shaped. The one exposure is the -X <hex> argv write of the large live item, briefly visible to same-user ps. That is Claude Code's own transport on every refresh, so it adds no new exposure class, but it is not zero.
  • Email validation is a security boundary. security -i re-tokenizes its command line, quotes included. I measured that a crafted email containing a " closes the service field, and a second -s then wins, writing an arbitrary Keychain item. So every email - from the command line, the accounts file, or even as reported by claude auth status - must match ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$, and the writer refuses any service name containing " or \ as a last line behind that.
  • One run at a time. The lock is a symlink at ~/.local/state/claude-acct/lock whose target is the owner's pid. ln -s creates the lock and publishes the pid in one atomic step, so no reader ever sees a lock without an owner. A dead owner's lock is removed only by whoever holds lock.break, after re-reading the lock under it, so two runs that saw the same dead pid cannot remove a lock a live run took in between.
  • Every failure is either "nothing changed" or "rolled back". Exit 2 and exit 3 are both tested states, not hopes.

Residual risk. Nothing makes the Keychain write and the .claude.json write one atomic step, and Claude Code takes no lock on the Keychain item. A running session still holding the old account can write it back: a token refresh into the Keychain, or its in-memory identity into .claude.json through its own config writer. The post-switch claude auth status check proves the switch landed. It cannot prove that a later write by such a session will not undo it. The rotation design in section 14 watches for exactly this.

Refresh-token rotation (reported by Mark Pavlyukovskyy, 2026-11-01). On his accounts each token refresh revoked the previous refresh token, so when two places held the same login, the first to refresh killed the other with invalid_grant. Here the two places are a parked slot and a running session still on that account: if the session refreshes after use parked its account, the slot holds a revoked refresh token and the next use back to it fails its sign-in. Two things limit it. use always re-parks the outgoing account from the live item at switch time, so a slot is only as stale as the last switch away from it; and since running sessions now follow a switch at their next request, the window is the gap before that request. A dead slot is repaired by one add. Re-saving the slot whenever such a session writes its token back to the Keychain would close it; that watch is not built.

11. Usage attribution

Claude Code's transcripts ($CLAUDE_CONFIG_DIR/projects/**/*.jsonl, subagent transcripts included) carry per-message token usage but not the account. usage joins them to the switch log: each message is charged to whichever account was live at its timestamp, deduplicated by message id. Before the first recorded switch, the live account is that switch's from; with no switches at all, it is whoever is live now.

$ claude-acct.sh usage --days 7          (example output, made-up numbers)
Token usage by account, last 7d (6 recorded switch(es))
account                         msgs      input     output  cache-write     cache-read
you@personal.example           20000      40000   15000000    150000000     6000000000
you@company.example             8000      16000    6000000     60000000     2400000000
you@fund.example                1000       2000     750000      7500000      300000000

This is an approximation. A running session that has not followed a switch is still charged to the new account, and everything before the first recorded switch lands on that switch's from account. In this example one account dominates because it was the live account for most of the week. The authoritative per-account numbers are the 5-hour and 7-day percentages on claude.ai and in /usage, and the statusline's rate_limits field.

Quota readings. record-limits keeps the statusline's rate_limits per account, and limits prints them. The payload names no account, so a reading is filed by two rules: each account has its own 7-day reset time, computed server-side from the token a request was sent with, so a reading whose reset time matches exactly one other known account's latest reading is that account's (a session that had not followed a switch yet); otherwise it is the live account's. Two accounts sharing one reset time fall to the live account. Ultra plans dropped the 5-hour window on 2026-10-30, so a reading with no 5-hour figure is kept as is, and a threshold trigger should read a missing 5-hour number as no 5-hour cap.

Keeping the higher reading. Within one reset window the used percent never goes down, so a lower reading carrying the same 7-day reset time is stale or out of order. record-limits keeps the stored percent when the stored reading's 7-day reset equals the new one's and its percent is higher; the 5-hour pair works the same way, keyed on its own reset time. A new window takes its own figure. Reported by Mark Pavlyukovskyy, who saw 60% and then 40% recorded in one window.

Token-launched sessions. A session started with CLAUDE_CODE_OAUTH_TOKEN runs on that token's account, which .claude.json never names, so the live-account rule would misfile its readings. Claude Code removes that variable from the statusline command's own environment (measured on 2.1.319: a control variable came through, the token did not), so record-limits looks for it in the environment of each process from its parent up to the first claude process (ps -E on macOS, /proc/<pid>/environ on Linux), counting matches only. For such a session the reset-time match is the only rule, over every known account including the live one; with no unique match the reading is dropped. Also reported by Mark.

No per-model cap. The statusline payload's rate_limits carries only five_hour, seven_day, and spend_limit (2.1.319). A per-model weekly cap such as Fable's is not in it, so a session can hit that cap while limits still shows headroom; the limits footer says so. Mark's session hit the Fable cap at about 79% of its weekly quota.

12. How it is tested

claude-acct.test.sh runs the real script against stubs: a fake security backed by files, a fake claude whose auth status reads the email from .claude.json (never from the token, matching the real CLI), and a throwaway CLAUDE_CONFIG_DIR. It never touches the live Keychain. 175 tests, all passing on 2026-11-09 (the token-session cases need node for a stand-in claude parent and print SKIP without it). Some of the ones that matter:

  • With CLAUDE_CONFIG_DIR unset (a stock install), the switch uses the unsuffixed Keychain item and ~/.claude.json, matching what the 2.1.314 binary resolves.
  • Every other .claude.json key is untouched, the file keeps mode 0600, and MCP logins in the live item are untouched.
  • A key a "running session" writes into .claude.json during the swap survives it (re-read under the lock).
  • A held config lock is waited for, then given up on with a full restore, and never stolen.
  • An identity write failure after a successful token write restores both, exits 3, and leaves no lock or temp file.
  • A switch claude never confirms is rolled back; one failed status read is retried and the switch stands.
  • A ~6 KB live item takes the argv branch and switches intact; small slot writes stay on stdin.
  • A crafted email is rejected on the command line, in the accounts file, and when claude itself reports one.
  • The round trip home, work, home restores the original token and identity exactly.
  • add opens the sign-in URL in the right Chrome profile and refuses when the login landed on a different account.

13. Compared with claude-rotator

Mark Pavlyukovskyy's claude-rotator solves the same problem. The two make different trade-offs because they assume different machines.

Questionclaude-rotatorclaude-acct.sh
Account modelA config directory per account, chosen when ccr starts a session.One config directory; the token and identity are swapped in place.
Running sessions when an account runs outStay on the account they started on until restarted.Every session moves: new ones at once, running ones at their next request.
Hooks, rules, skills, historyShared through a fixed symlink list per account dir.Shared, because there is only one directory.
MCP loginsOne Keychain namespace per account dir, so one sign-in per server per account.Untouched. Only claudeAiOauth moves.
Concurrent accountsYes: different sessions can run on different accounts at once.No: one live account at a time.
Fallback when every subscription is outKimi on Fireworks, then OpenRouter, then an Anthropic API key.None. Requests always go through the unmodified claude binary on a subscription I own.
Chrome-One profile per account, brought forward on switch.
Usage across parked accountsPolled.Not polled. record-limits files each statusline reading under its account; parked accounts show their last reading.

If you run short sessions on a clean ~/.claude, the rotator's model is simpler and gets you concurrency. If your config directory is your whole operating environment and your sessions live for days, swapping in place is the better fit. I took two ideas from the rotator for the next step: its ordering rule and its idea of checking that a usage reading belongs to the account you think it does.

On terms: like the rotator's README, this only rotates subscriptions I own, for my own use. No token is ever handed to another process, leased, or sent anywhere except by the claude binary itself.

14. What comes next: automatic rotation

The script is the mechanism. The policy - when to switch, and to which account - is the next piece. It is designed, not built. The plan is a switch that runs a protocol rather than a bare use:

  1. Hold. Pause dispatch and wait for a safe boundary: no deploy in flight, no session mid-git push or mid-browser-tool call. Give up after 10 minutes and say what is blocking.
  2. Check the target: a saved token, a login not known dead, and headroom above the threshold.
  3. Swap with claude-acct.sh use.
  4. Confirm per session. For 15 minutes, check that each session's quota readings move to the new account's reset window (the same signal record-limits uses). A session still on the old one is flagged.
  5. Watch for write-back for 24 hours (the residual risk in section 10), and raise it if seen.
  6. Resume dispatch and log the switch as an audit event.

Ordering, credited to the rotator: unused headroom disappears when a window resets, so the next account is the one whose window resets soonest among those with headroom left. Maxed-out accounts and dead logins go last.

Automatic rotation switches on a threshold rather than at exhaustion, so sessions rarely stop at all. It runs only under a standing policy you turn on explicitly, naming the accounts it may use and an expiry of at most 7 days, limited to one automatic switch per 30 minutes and four per day, and it stops and asks rather than thrash if no account qualifies. A missing 5-hour figure (Ultra plans) counts as no 5-hour cap.
